What Stamped is

Stamped helps plant teams choose, assign, and verify the next operating action across energy, cost, time/throughput, continuity/flow, and short-horizon exceptions. Plant data enters through L1 connectors, is stored in the L2 universal repository, and becomes Findings in L3. L4 recommends actions and drafts card proposals; L5 owns live workflow, M&V, and the ledger; L6 is the control room. Layers communicate only through versioned contracts in stamped-external (ADR-030). What is BUILT means code on main with tests—not production deployment. No integration is live at any customer plant; verified savings to date are ₹0. SYS-00 — Stamped end-to-end map

architecture · answers: What are the layers of Stamped and how does plant data become a decision card?

Stamped spans L0 plant equipment through L6 control room, with every hop governed by versioned contracts in stamped-external. Plant readings enter via L1 connectors, land in the L2 universal store, and feed L3 detection that emits Findings. L4 turns emitted Findings into decision cases and card proposals, but the live L5 card ingest path is still designed. L5 closes the loop with workflow, M&V, and ledger rows while L6 gives operators a BFF-backed UI. Dashed edges mark designed cross-layer hops; nothing in this map is live at a customer plant yet.

SYS-01 — Contract & boundary map

dataflow · answers: Which contracts (schema@version) cross each layer boundary, and who owns them?

This dataflow names the contract family at each boundary from L1 publish through L6 consumption. Telemetry and commercial records are classified at the edge of the SSOT catalog; deprecated prescription shapes stay dashed. Authority for schema versions remains contracts/ plus ADR-030 framing. Card proposals are drawn as designed because L4 emits them while L5 still ingests prescriptions only.

SYS-02 — Runtime: data batch to decision

sequence · answers: When a machine reading is taken, what runs until a card proposal exists?

A PLC batch is buffered on the edge, published MQTT QoS1, deduped in connectors-cloud, and relayed into L2 Timescale. Detection runs on demand—scheduler code exists but is not deployed—read L2, and emit Findings through the L3 outbox. L4 consumes inbox jobs, runs the stage graph, and reaches CardSink, which targets POST /cards on L5 as a designed stub. Each async hop is at-least-once with dedupe called out in layer manifests.

SYS-03 — Runtime: Ask analyst question

sequence · answers: When someone types a question in the control room, what happens until an answer appears?

Operators type in L6 web and the BFF forwards POST /analyst (built). On main today the L4 analyst API always responds 503 ASK_MOVED because the Ask ReAct orchestrator is retired (AskRetired in graph.py). Tool and retrieval libraries remain built but are not wired to a live Ask path; the dashed segment shows the retired ReAct design (per-turn tool budget in L4-07), not production behaviour.

SYS-04 — Runtime: card closure and M&V

sequence · answers: After an owner marks a card done, how does Stamped decide whether savings are real?

Owners act via L6 or messaging; L5 records workflow transitions while a worker polls L2 for stabilize-window evidence. ops_confirmed ledger appends are distinct from deferred bill-verified claims (ADR-020). L6 polls L5 today rather than taking inbound HMAC webhooks; learning back to L4 remains designed.

SYS-05 — Operating loop across layers

workflow · answers: Which layer owns each step of the product loop and where are the human gates?

The product loop is detect (L3), recommend (L4), assign and verify (L5), with human act steps in L6. Gates include certification, can_emit, pending_stamped_review, and ops clearance. Learn back into L4 is dashed because hindsight memory is designed only.

SYS-06 — Life of one plant condition

lifecycle · answers: What states does a single issue pass through across layers, and who owns each state?

One condition moves from L3 candidate/emitted Finding through L4 proposal, across a designed hop into a live L5 card, then to ops_confirmed and an append-only ledger row. lab_only and shadow paths are omitted here for width; see L3C diagrams for detection internals.

SYS-07 — Deployment and trust boundaries

architecture · answers: Where does each component run, which networks are separated, and where do secrets stay?

edge-agent stays outbound-only on plant OT networks; context-agent sits on plant IT. Stamped cloud hosts MQTT, connectors, L2–L6, and generic service-key seams to LLM and notification providers. No hostnames or customer identifiers appear on this map.

SYS-08 — Built vs designed status map

architecture · answers: Which parts exist in code today, which are only designed, and what is not live?

Status tags summarize pinned manifests: edge and L2 methods are built, context poller and L4 memory are partial, PathScheduler is built-but-not-deployed, L5 /cards and Hindsight are designed or deferred. Verified savings remain ₹0 with no live integration.

SYS-09 — Evidence and money lineage

dataflow · answers: Where does a rupee figure come from, and which steps may create or change it?

Rupee estimates may only originate in the L3 calculator (calculator_ref) and surface as Modeled evidence on Findings and cards. L4 must cite that ref; L5 alone appends realised ledger rows after ops_confirmed. L6 sanitizes claim status so ops_confirmed is never shown as bill-verified.
